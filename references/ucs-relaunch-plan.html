Implementation approach — flat-file i18n, no CMS

One JSON translation file per language (en.json, cs.json, pl.json) + one shared HTML template. Eleventy (11ty) builds three complete sets of static pages at deploy time. Adding a new page means creating one template — the build generates it in all three languages automatically. A CloudFront Function on the root / reads the visitor's Accept-Language header and routes to the appropriate version. No CMS, no server, no moving parts.

06

ThingsBoard Demo — Dashboard Specification

The demo must be immediately accessible without login — a visitor lands on the page and sees a live (or near-live) weighing system dashboard with no friction. The system being shown is a scale with 8 load cells, typical of a bridge scale or truck scale installation.

Cross-domain challenge — decision needed

ThingsBoard is currently running on a separate domain. Three approaches exist to embed or connect it from unifiedcloudsensors.com. They differ in development effort, visual integration quality, and what changes are needed on the ThingsBoard server. Pick one before Phase 3 begins.

Approach How it works Effort Visual fit Requirement
A — Public iframe
Simplest
Configure a Public Dashboard in ThingsBoard → embed via <iframe> on the demo page. ThingsBoard shows its own UI inside the frame.
 S (1 d) ThingsBoard UI only
Set X-Frame-Options: ALLOWALL (or remove header) in ThingsBoard server config (thingsboard.yml). Mark dashboard as Public in TB settings.
B — REST API + custom charts
Recommended
JavaScript fetches data from ThingsBoard REST API. Site renders its own spider plots, tables, analytics using Chart.js. Full visual control; matches brand perfectly.
 M (4–6 d) Full brand match
ThingsBoard API must allow CORS from unifiedcloudsensors.com. A read-only API token or public device credentials stored in the page JS.
C — Move TB to subdomain
Point iot.unifiedcloudsensors.com → ThingsBoard server via DNS/proxy. Same-origin restrictions lifted; iframe or API both work cleanly.
 S (1–2 d) Either
DNS A record + reverse proxy (nginx/CloudFront origin) in front of the ThingsBoard server. ACM cert for the subdomain.
Recommendation: Option B (API + custom charts) with Option C as the setup step

Move ThingsBoard to iot.unifiedcloudsensors.com first (Option C — one afternoon of DNS + nginx work). Then use the REST API to pull data and render branded charts (Option B). This gives you full visual ownership of the demo, a URL that looks like yours, and no dependency on ThingsBoard's UI ever breaking the embed. The public dashboard can still be used as a fallback link ("open in ThingsBoard") for users who want the full-screen experience.

What the demo page must display:

Spider / Radar Plot
  • 8 axes — one per load cell
  • Current load as % of nominal capacity per cell
  • Ideal load = perfectly symmetrical octagon
  • Imbalance highlighted in amber/red
  • Animated update on data refresh
Data Table
  • Cell ID · Current load (kg) · % capacity
  • Zero-point drift (mm / mV)
  • Status: OK / Warning / Fault
  • Last calibration date
  • Sortable columns, color-coded status
Analytics Panel
  • Load trend per cell — last 12 months
  • Drift trend — zero-point shift over time
  • Total scale throughput chart
  • Anomaly markers on timeline
  • Date-range picker (M500 historical data)
Summary Bar (top of page)
  • Total current load (kg / % capacity)
  • System status: All OK / n cells warning
  • Most loaded cell ID
  • Days since last calibration
  • Data freshness timestamp

Note from site audit

The existing .eu ROI page (/inpage/uspora-a-navratnost-nakladu-sensweight/) lists cost-reduction categories but contains no specific numbers or formula — it's narrative only. The new calculator must be built with real figures. Please share the ROI attachment you referenced so we can wire the exact formula.

Likely Inputs (from site content)

  • Current service visits per scale per year
  • Average visit cost (travel + labour, €)
  • Unplanned downtime hours/year

Outputs to Display
  • Annual service visit savings (€)
  • Annual measurement loss savings (€)

Open Questions — Needs Your Input

Q1
Which cross-domain approach for ThingsBoard: A (public iframe), B (REST API + custom charts), or C (move TB to iot.unifiedcloudsensors.com)?
See §06 for the comparison. Recommendation is C then B — move to a subdomain first, then build branded charts. This decision gates Phase 3 work.
Q2
Please share the ROI calculation document/attachment you mentioned.
The existing .eu ROI page has no numbers — only narrative. The calculator needs the actual formula, input parameters, and typical values your sales team uses.
Q3
Do you have access to the AWS prod environment, or do we set it up fresh?
Determines whether we configure new S3/CF resources or connect to an existing AWS account with existing IAM policies.
Q4
Which YouTube videos should appear in the video gallery?
We need the specific video URLs or a channel link. We can pull titles and thumbnails from those URLs to build the gallery.
Q5
Is the M500 a specific customer installation or a UCS reference system?
Affects how we label it on the demo page: "live customer installation" vs. "UCS reference measurement site." Also determines any access/privacy constraints on showing the data publicly.
Q6
Should the demo be open to all visitors, or behind a "request access" gate?
An open demo generates more self-qualified leads. A gate (simple form or Cognito password) adds friction but may be required for commercial sensitivity of the M500 data.
